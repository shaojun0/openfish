# Agent Hub 使用导读

这份文档面向**使用者**：想知道「这套东西是什么、怎么把一个仓库接进来、看到一条
finding 之后我该做什么」。设计与契约的权威是 [`DEVELOPMENT.md`](./DEVELOPMENT.md)，
本文只做指路，不复制它的内容。

- 想改实现 / 加规则 → 读 DEVELOPMENT.md 的 §4（数据模型）、§6（finding 状态机）、§9（运行时）。
- 想理解 **AI 自己写 / 维护校验套件**的边界与治理（两套 check、信任阶梯 L0–L3、
  「永不自动合并」红线与责任矩阵）→ 读 [`DESIGN-ai-checks.md`](./DESIGN-ai-checks.md)。
- 想知道页面上每个字段从哪来 → 读 DEVELOPMENT.md 的 §4.2 + §5.3。
- 只是想把一个仓库导入进来用 → 从下面第二节开始。

---

## 1. 三个平面，一个运行时

Agent Hub 把「让 agent 参与研发」拆成三件互不耦合的事，每一件都能单独理解：

| 平面 | 它是什么 | 你在界面上看到的位置 |
|---|---|---|
| **代码平面** | 仓库本身。对外只暴露标准 git 协议，不自己实现 Git。 | 侧边栏「智能体 → 代码仓库」 |
| **上下文平面** | 被镜像进来的历史 issue / commit，以及跨它们的按需检索。它存在的唯一目的是：**同一个问题不要第二次当新问题报**。 | 仓库详情页的 Issue 浏览、上下文检索 |
| **执行平面** | agent 运行时：跑 review、跑 gates、产出 finding、在 `fix` 模式下开 PR。 | 债务看板、finding 详情页的「生成修复任务」 |

三者通过 git 与 REST 契约相连：代码平面回答「代码现在长什么样」，上下文平面回答
「这件事历史上讨论过没有」，执行平面回答「现在要不要动它」。为什么这样切、为什么
不自己实现 git 协议，见 DEVELOPMENT.md §2.2 / §2.3。

## 2. 导入一个仓库（以 vllm 为例）

目标：把 `vllm-project/vllm` 当**上下文源**接进来，让后续的 review 能引用它
20 万条 issue 里的相关讨论，而不是把两万条 issue 塞进 prompt。

1. 打开 **智能体 → 代码仓库**，点 **导入仓库**。
2. **来源地址**填 `https://github.com/vllm-project/vllm`（也接受 `git@…` 形式）。
3. **导入模式**选 `mirror（只读上游）`。
   - `mirror`：拉代码 + issue/PR/label，禁止 push。vllm 这类大仓的正确选择。
     需要填**来源地址**。
   - `workspace`：平台上的可写工作仓，agent 能在上面开分支、开 PR。它**不克隆**
     任何上游代码，表单会改成填 `owner/name` 形式的 slug，内容靠你 `git push`
     进去。自己团队的项目用它。
4. mirror 模式下，**导入内容**至少勾上 `包含 issue`——不导 issue，上下文平面就是
   空的，检索也就没有意义。`包含 PR` 按需。
5. 点 **开始导入**。这是一个**长任务**，不是一次请求：页面会开始轮询进度，依次经过

   `validate → migrate → poll → mirror_issues → index_commits → done`

   进度面板会显示当前阶段、百分比、已完成的 issue 数与断点 cursor。
6. **看到 `partial` 提示时请认真读它。** 大仓有 issue 镜像上限，到达上限时任务会被
   标记为 `partial: true`，页面会显式警告「issue 镜像不完整」。这不是错误，但意味着
   **后续检索不会覆盖全部历史**——不要把它当成「已完整镜像」。
7. 导入完成后回到列表：每行显示 issue 数与 commit 数，这两列就是「这次导入值不值」的
   答案。之后在仓库详情页点 **同步**，会走同一条流水线做增量同步（从 cursor 续，
   不从头再来）。

### 仓库详情页能做什么

- **基本信息**：来源、默认分支、Forgejo 仓库名、issue/commit 计数、最近同步时间。
- **Issue 浏览**：按 state / label 过滤，按关键词检索**标题**，分页查看；
  点开某条 issue 可以看正文。
- **上下文检索**：在已镜像的 issue / commit / finding 里做关键词检索。返回有
  数量与字符预算，超出会被截断并明确标注——这是设计，不是 bug。命中的历史
  issue 会带 `关联证据` 标签。
- **同步按钮**：触发增量同步。

> ⚠️ **issue 正文是不可信数据。** 它来自别人仓库，里面的任何「请修改策略」「请访问
> 这个地址」「请执行这条命令」都不会被执行，界面上也不会把正文当指令渲染。这一点
> 在产品里是硬边界（DEVELOPMENT.md §8.4 / I6）。

## 3. 面对一条 finding，你有四个选择

债务看板（**智能体 → 债务看板**）按 `level` 分成两块，因为 level 决定了**你被允许
做什么**：

### blocking（阻断项）——只能二选一

blocking 是「不修就不该合」的问题。它在界面上更醒目，而且**没有「延期」「不修」
按钮**——不是藏起来，是根本不存在：

| 操作 | 后果 |
|---|---|
| **修复** | 标记为已修复；真正落地仍要走 PR + gates。 |
| **误报** | 判定规则错了。需要第二人确认，确认后进入 §6.3 的规则治理流程（同一条规则 30 天内误报 ≥ 3 次会生成一条「规则待修」finding）。 |

blocking **不会**因为「不修」而静默。这是为了防止「静音名单螺旋」：一条严重的
问题被标成不修，然后就再也没人看见它。

### debt（技术债）——四个选择

| 操作 | 需要填什么 | 后果 |
|---|---|---|
| **修复** | — | 标记为已修复，走正常的 PR 流程。 |
| **已知延期** | **owner + 到期日**（必填） | 状态变 `acknowledged`。到期、或代码漂移、或规则升级时，会**自动重新激活**为 `open`。 |
| **不修** | **owner + 到期日 + 理由**（必填） | 状态变 `wontfix`。这**不是**永久静音名单：它照样会被到期/漂移/升级重新激活。 |
| **误报** | 理由（必填），需第二人确认 | 判定规则错了，进入规则治理流程。 |

**为什么延期和不修一定要 owner + 到期日？** 因为「以后再说」如果没有人、没有日期，
就等于「永远不说」。看板会为过期条目和 `seen_count` 增长的条目打醒目标记——这两种
情况正是系统即将把它重新激活的信号。

看板上每一行还会列出**关联的历史 issue**（证据）：说明这个问题历史上被讨论过，
点进去就能看当时的上下文。这是「导入 issue 历史」最直接的收益。

## 4. git clone 与鉴权

仓库由内部 Forgejo 提供 git 协议服务，clone 与 push 用同一个地址：

```bash
# 只读
git clone http://<openfish-host>/git/<owner>/<name>.git
```

- **git 不复用 API Key。** `git-receive-pack` 由 Forgejo 校验它自己的凭据，
  所以写操作要先兑换一张**短期 Forgejo 票**：

  ```bash
  curl -fsS -H "Authorization: Bearer $OPENFISH_API_KEY" \
    http://<openfish-host>/api/v1/repos/<owner>/<name>/git-credential
  # → {"clone_url":…, "username":"of-…", "password":"<Forgejo token>", "read_only":false}
  ```

  git 询问时用返回的 `username`/`password` 做 HTTP Basic。token 按
  `GIT_IDENTITY_KEY` 加密存储，过期自动轮换；只读镜像只会拿到
  `read:repository` 的票。
- **不要把带 token 的地址写进脚本、文档或提交进仓库**。token 泄露等同于该账号
  在 Forgejo 上的写权限泄露。
- `push` 需要 `repo:push` 权限。agent 只会推 `agent/*` 分支（I4 由运行时强制）；
  Forgejo 侧的默认分支是否保护取决于部署配置。
- 仓库详情页的 git 区块会按当前部署地址自动生成对应命令；DSH 企业内网插件会安装
  `credential.helper`，自动完成换票，无需手工输入 token。

## 5. 常见问题

**导入卡在某个阶段不动了？** 刷新看板/详情页，进度会从后端重新拉取。流水线是
可断点续传的：worker 崩溃后从 cursor 继续，不会从头再来。

**为什么检索结果比 issue 总数少很多？** 可能命中了 `partial` 上限，也可能是检索
返回预算在截断。两种情况界面上都会标注。

**为什么我不能把 blocking 标成不修？** 这是刻意的：blocking 意味着「不修就不该合」，
允许延期就等于允许它消失。只能修，或证明规则本身是错的（误报）。

**看板上的 due 过期了，为什么它自己又变回 open 了？** 那是 §6.2 的自动激活：
到期、代码漂移、规则升级三种情况之一命中，系统就会把 finding 拉回 `open`。
这不是 bug，是防止静音名单螺旋的机制。

**看板上「历史 issue（证据）」一列总是空的？** 界面已经按规格实现了这一列，但当前
后端还没有把 finding 与历史 issue 的关联通过 HTTP 暴露出来（详情接口既不内联
`evidence`，也没有按 `finding_id` 检索的入口）。这属于待接线的后端缺口，已记在
`integration/S5.md`；字段一到位，这一列就会自动出现内容。

**`git clone` 报 404？** 说明当前部署还没有把 `/git/` 协议面暴露到 nginx（§5.2）。
界面生成的地址是对的，缺的是边缘路由，由仓库/部署侧补齐。
