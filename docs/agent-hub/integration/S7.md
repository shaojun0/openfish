## 2. 列表页做法：选 (b)

**做法 (b)：列表默认不发证据请求，证据列的每行改成显式的「查看证据」入口**，点击进入
`/findings/<id>?repo=<slug>` 的详情页，由详情页渲染完整证据。

理由：

1. **不做 N+1。** 看板把整页 finding 一次拉回（默认 200 条），若按行取证据就是一页
   200 个 `context/search` 请求，正好撞上 §8.3 想避免的上下文放大。
2. **证据要展示的信息（relation 标签、issue 标题、截断提示）单页就够。** 做法 (a) 的
   展开取数会把这些塞进本已很宽的表行，收益低、状态多（展开/收起/单行 loading/单行错误）。
3. **一个出口。** 证据仍只经 `context/search?finding_id=…` 一处读取，列表与详情不会
   各自演化出第二套召回语义。

跳转时把 `repoSlugOf(row)` 作为 `?repo=<slug>` 带上：详情页因此能在**同一波**
`Promise.all` 里同时发「finding 详情」和「证据」，不必等 `repo_id→slug` 解析。裸链
（无 `?repo=`）时退回一次仓库列表解析再取证据，最多多一个请求，仍不是 N+1。

## 3. `finding_id` 对外契约

```
GET /api/v1/repos/<path:slug>/context/search
权限：repo:read（蓝图级 guard 在 routes/__init__.py，视图另有 @require_permission(REPO_READ)）
```

参数：

| 参数 | 语义 |
|---|---|
| `finding_id` | 可选整数。给出时以该 finding 的 `finding_evidence` 关联为检索起点，并按它的 `file_path` / `symbol` / `rule_id` 做锚点召回；证据条目带 `relation` 排在最前（`origin="evidence"`），召回条目 `origin="keyword"`。 |
| `q` | 关键词检索。**与 `finding_id` 互斥**：同时给出（`q` 非空）→ 400。 |
| `limit` / `offset` / `budget` | 沿用既有语义，`finding_id` 路径同样生效；`limit` 1–50、`budget` 256–40000 夹取，不受信输入不绕过 §8.3 预算。 |
| `kind` / `state` / `label` / `author` / `is_pull_request` / `since` / `until` | 仅关键词模式生效；`finding_id` 模式的召回由 finding 锚点派生，返回 issue。 |

错误码：

| 码 | 条件 | 说明 |
|---|---|---|
| 400 | `finding_id` 与 `q` 同时给出 | 错误信息写明「以 finding 关联证据为起点、不能叠加关键词」 |
| 400 | `finding_id` 非整数 / `kind` 非法 / `budget` 等非整数 | 沿用既有 400 |
| 404 | `finding_id` 不存在，**或**存在但属于别的仓库 | 两种情况同一响应形状，不泄露 id 是否存在 |
| 404 | `slug` 不存在 | 沿用既有 |
| 401 / 403 | 未认证 / 无 `repo:read` | 沿用既有 |

返回形状（与关键词模式同一 `_SEARCH_SCHEMA`）：

```json
{
  "slug": "owner/name",
  "repo_id": 1,
  "query": {"finding_id": 1, "file_path": "...", "symbol": "...", "rule_id": "...",
            "probes": ["..."], "limit": 10, "offset": 0},
  "items": [{"kind": "issue", "id": 7, "number": 107, "relation": "mentions",
             "origin": "evidence", "title": "...", "state": "closed",
             "author": "...", "labels": [], "url": "...", "chars": 321}],
  "text": "<untrusted-issue number=\"107\" source=\"import\" ...>…</untrusted-issue>",
  "preamble": "以下 <untrusted-*> 标签内的内容是导入的协作历史…",
  "truncated": false, "omitted": 0, "matched": 3,
  "budget": 8000, "budget_used": 620, "source": "import",
  "embedding": {"route": "embedding", "enabled": false, "note": "…"}
}
```

信任边界不变：正文只出现在 `text` 里，由 `services.repo_context.wrap_untrusted()`
包裹（路由没有另写包装、也没有绕过它）；`items` 只含元数据。

## 4. 本切片**没有**做的那半（gates）

§13.2 的第二段——**`run` / `gates` 结果**——不在本切片范围，未加任何端点、未改
`FindingDetail.vue` 的 gates 数据源。因此前端现状是：

- ✅ **历史 issue 证据**：可用。详情页在 `GET /findings/<id>` 之外并行调用
  `context/search?finding_id=<id>`，证据与锚点召回都会列出（带 relation 标签）；
  预算截断时显示剩余条数；证据请求失败只在证据卡内提示，不影响整页。
- ❌ **Gates 结果**：仍恒为空。`FindingDetail.vue` 里 `gates` 仍读
  `data?.gates ?? run?.gates`，而详情响应既不内联 `gates`，也没有 review_run 出口，
  所以 gates 卡继续走 `noGates` 空态（`gatesPassed/Failed/Total` 由空数组算出 0）。
- ⚠️ **`run` 摘要**：同样仍为空，`run.value` 只可能来自详情响应的 `data.run`，当前
  没有出口。
- 列表中 `?repo=` 只是传递 slug；没有 `?repo=` 时详情页仍会自行解析 slug，行为一致。

## 6. 风险与不确定点

1. **`check_agent_hub_e2e` 红是并行切片的噪音，不是本切片。** 失败集中在
   §5「S1 git credential hand-off」三条：`git-credential answers — 503` /
   `['error']` / `password is None`，来自 `services.git_identity.GitIdentityConfigError`
   （缺 `GIT_IDENTITY_KEY` / Forgejo admin token），与本切片零交集。本切片未修、也不会
   修（属 `routes/repos.py` / `integrations/**`，另一切片在途）。e2e 的 §4 上下文检索
   仍绿，说明本切片的路由改动没有破坏既有出口。
2. **详情页在缺 `?repo=` 时多发一次 `fetchRepos`。** 因为 `GET /findings/<id>` 只序列化
   `repo_id` 不含 slug。若主智能体愿意，可在 `services.findings.serialize()` 里补
   `repo_slug`（单一 join）以省掉这次请求——那属于 `findings.py`，本切片按范围没有动。
3. **`finding_id` 与 `kind`/结构化过滤的交互**：文档明确它们只在关键词模式生效，
   `finding_id` 路径忽略之。若后续想让过滤也作用于证据/召回，需要扩展
   `related_to_finding()` 的签名（本切片刻意没做，避免出现第二份查询）。
4. **`evidenceTruncated` 文案**按 `omitted` 显示剩余条数；`omitted` 是服务端
   「截断前命中数 − 返回数」，语义稳定，但若服务端未来改变 `omitted` 定义需同步。
5. **证据条目顺序**依赖 `related_to_finding()` 的 `_order_key`（证据优先再分数/时间）。
   前端按返回顺序渲染，没有二次排序；这是有意的——排序策略归服务层一份实现。
