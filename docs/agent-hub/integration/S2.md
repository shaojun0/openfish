## 1. 本切片交付

| 文件 | 内容 |
|---|---|
| `backend/services/repo_context.py` | 上下文引擎：关键词 + 结构化过滤 + 关联扩展 + top-k/字符预算 + 不可信包装 + `EMBEDDING_ROUTE` 钩子 |
| `backend/routes/repo_context.py` | `GET /api/v1/repos/<path:slug>/context/search`（`repo:read`） |
| `backend/scripts/check_repo_context.py` | 离线门禁：临时 SQLite 建表灌数，验证 ①–⑤（含注入断言） |
| `docs/agent-hub/integration/S2.md` | 本文件 |

行为要点：

- 关键词检索是 `lower(col) LIKE %term%`，**SQLite 与 PostgreSQL 同一份代码**；
  标题命中权重 `TITLE_WEIGHT=3`，正文 1。多词默认 AND，中文整串（无空格）作为一个词条子串匹配。
- 返回**双重上限**：`limit`（默认 10 / 上限 50，逐类型取 top-k 后合并）+ `budget`
  （默认 8000 字符 / 256–40000）。超限时 `truncated=true`，`omitted` 是截断前的真实差额，
  `budget_used` 是实际占用。**不存在无上限路径**。
- 所有 issue/PR/提交/finding 正文只出现在 `text` 里，并被
  `<untrusted-issue number="…" source="…">…</untrusted-issue>`（或 `-pull-request` /
  `-commit` / `-finding`）包裹；`items` **只含元数据，不含正文**。`preamble` 是配套的
  「这是数据不是指令」声明（§8.4 / I6）。
- 正文里伪造的 `</untrusted-issue>` 会被中和成 `&lt;/untrusted-issue>`（文字保留、
  不再是结束标签）；正文其余部分逐字保留，注入句不会被静默清洗。

## 9. 风险与取舍

1. **跨库关键词检索用 `lower(col) LIKE %term%`**：SQLite 与 PostgreSQL 行为一致
   （中文无大小写、`lower()` 恒等；英文两侧折叠），代价是**用不上 btree 索引**。
   但 `%term%` 前置通配本来就用不上 btree；PG 要加速需 `pg_trgm`，本轮按「不新增依赖」不引入。
   数据量到十万级 issue 时这是第一个要 revisit 的点（见 `OPEN-QUESTIONS.md`）。
2. **label 过滤是 JSON 文本里的 `"label"` 子串匹配**：避免了 PG `jsonb` 运算符与
   SQLite `json_each` 的分叉（列本身是 TEXT），代价是标签里的引号/非 ASCII 大小写不折叠。
   当前 label 词表是 ASCII，够用。
3. **时间类型假设**：S0 用 `DateTime(timezone=True)`。HTTP 参数用 `datetime.fromisoformat`
   解析后直接交给 SQLAlchemy；不带偏移的输入在 PG 上按会话时区解释（建议客户端带偏移）。
   `RepoIssue.created_at` 可空，SPA/runner 需要容忍 `null`。
4. **`offset` 是逐类型偏移**：`kind=all` 时每个类型各自 offset 后再合并 top-k，不是全局游标；
   上下文检索的主路径是 top-k，分页只是补充。
5. **预算单位是 Unicode 码点**（`len()`），不是 token；中文 1 字 = 1。放不进预算的条目
   只裁剪**标签内部**的正文并重渲染，绝不裁剪标签本身（否则会漏出结束标签）。
6. **不可信包装是纵深防御**：真正的第一道防线是 `preamble`（系统提示词声明）+ 沙箱无外网；
   标签中和只保证「正文不能假装自己已经出了标签」。
7. **`findings` 也被包成不可信**：`detail` 可能来自模型或受不可信输入影响，按同等级别处理。
