## 2. §5.3 与落地实现的差异，以及前端的处理

写前端时按 §5.3 实现；S1–S4 落地后逐一对照**实际代码**（`backend/routes/*.py`、
`backend/services/*.py`）做了对齐。下表是每一处差异与前端当前行为。

| # | §5.3 / 规格 | 落地实现 | 前端处理 |
|---|---|---|---|
| 1 | `POST /repos/import` body `{source_url, mode: mirror\|workspace, include_issues, include_prs}` | `routes/repos.py`：`mode ∈ {code, code+issues, issues}`，**无 `include_issues`**；始终建 `kind="upstream"`；workspace 走 `POST /repos` | 对话框保留 mirror/workspace 单选：mirror 发 `mode = include_issues ? 'code+issues' : 'code'`；workspace 改为填 slug 并调 `POST /repos {slug, kind:'workspace', default_branch}`。两种路径都真实可用，已在对话框内切换字段 |
| 2 | `ImportJob.id` | `job_payload()` 用 `job_id`，仓库 slug 在 `repo` | `asImportJob()` 归一化 `job_id → id`、`repo → repo_slug`；`fetchImportJob` 也走它，否则轮询后 `job.id` 变 undefined |
| 3 | `ImportJob.phase` = migrate…build_search | `JOB_PHASES = validate, migrate, poll, mirror_issues, index_commits, done`（**有 validate，无 build_search**） | `KNOWN_PHASES` 以落地值为准并保留 `build_search` 前向兼容；i18n 补 `validate` |
| 4 | `Finding` 含 repo / evidence | `serialize()` 只有 `repo_id`，**不内联 evidence / gates / run**；`GET /findings/<id>` = `{finding, events}` | 看板用 `fetchRepos` 建 `repo_id → slug` 映射做仓库列与 evidence 链接兜底；evidence / gates 区块在缺字段时显示空态（见 §3 待接线 1、2） |
| 5 | `decide` body `{action, owner, due, reason}` | `_DECIDE_BODY` 另有 `confirmed_by`，且 `false_positive` **必须**由第二个账号确认（服务端校验 `confirmed_by != actor`） | 决策对话框在 `false_positive` 时多一个「确认人」必填项，并前端校验不能等于当前用户 |
| 6 | `POST /findings/<id>/fix` → `AgentTask` | `routes/findings.py` 返回 `{finding_id, task_id, kind, queued}` | 按回执处理：`queued === false` 时提示"未入队"且不造任务；否则用 `task_id` 组装本地任务卡 |
| 7 | `GET /agent/tasks/<id>/log` → 日志 | 返回 `{task_id, status, result_ref, log_ref}`（**引用而非正文**），且要 `agent:admin` | 按钮以 `agent:admin` 门控；弹窗顶部说明"这是引用不是正文"，内容按 `result_ref` / `log_ref` 分行展示 |
| 8 | `GET /repos` / `/repos/<slug>/issues` 分页 | 都是服务端分页，返回 `{items,total,page,per_page,pages}`，`per_page` 上限 200 | repos 取一页 `per_page=200` 后前端分页，并用 `total` 在超页时显式提示；issues 用 `TablePager` 直接驱动服务端分页 |
| 9 | `GET /findings` 无分页 | 服务端 `limit`（默认 200）/ `offset`，返回 `{items,total,limit,offset}` | 用 `total` 与 `items.length` 比较，超出时显示"仅显示最新 N / M 条"提示 |
| 10 | `/context/search` 返回 issue/commit/finding 混合 | `_ITEM_SCHEMA`：`kind/number/title/message/sha/file_path/symbol/state/status/relation/origin/score` 等，**没有 `snippet`**，另有 `omitted`/`budget_used` | `ContextHit` 按真实字段建模；`origin === 'evidence'` 加「关联证据」标签；`omitted` 显示在截断提示里 |
| 11 | issue 检索 | `q` 只匹配 **title**（`routes/repos.py` ILIKE title） | 输入框文案改为「按标题关键词检索」 |
| 12 | issue 详情「正文 + 评论」 | 返回 `body` + `body_html`，**没有评论表/评论字段** | 正文用 `body_html`（`services.markdown` 以 `html=False` 渲染，原始 HTML 被转义，与文档页同等信任级）渲染，回退到等宽纯文本；评论区在缺字段时显示"暂无评论" |
| 13 | 权限点 | S1–S4 各自声明常量，需 S0 落到 `auth/permissions.py` | 路由 meta 与按钮门控用 §5.1 的 code；smoke 权限桩按 §5.1 全量写死 |

## 3. 需要主智能体接线的事项

1. **finding ↔ issue 证据没有 HTTP 出口（最重要）。**
   `services/repo_context.related_to_finding()` 已实现（含 `_evidence_candidates`），
   但 `routes/repo_context.py` 的 `/context/search` **不接收 `finding_id`**，也没有
   `GET /findings/<id>/related`；同时 `findings_service.serialize()` 不内联
   `evidence`。因此看板的「历史 issue（证据）」列与 FindingDetail 的 evidence 区块
   目前必然是空态。**二选一即可**：搜索路由加 `finding_id` 参数并透传（约 2 行），
   或 `serialize()`/详情接口内联 evidence。
2. **gates / review_run 没有 HTTP 出口。**
   FindingDetail 的「Gates 结果」需要 `{gates:[…], run:{gates_total,gates_passed,
   gates_failed}}`（§9.4），当前 `GET /findings/<id>` 不返回，且没有 review_runs
   路由。建议在详情响应里内联最近一次 run 的 gates 摘要。
3. **`/git/` 协议面尚未在 nginx 暴露。** RepoDetail 生成的 clone 地址是
   `http://<host>/git/<forgejo_repo|slug>.git`（§5.2）；`docker/nginx/nginx.conf`
   与 dev 的 `vite.config.ts` 都还没有 `/git`。这是 S1 的交付（§10 已列），本切片
   按纪律不改 `docker/**` 与 `vite.config.ts`。
4. **权限点落地。** `repo:read` / `repo:write` / `repo:push` / `finding:read` /
   `finding:decide` / `agent:run` / `agent:admin` / `policy:write`（§5.1）必须进
   `auth/permissions.py`。若最终 code 有改动，`scripts/smoke-render.ts` 的权限桩
   与路由 meta 必须同步。
5. **冒烟清单是共享验收点。** 后续切片新增页面请继续往 `EXPECTED` 里加，不要另起
   脚本。

## 4. 本切片无法自证的部分

1. **真实数据渲染。** `npm run smoke` 用 `renderToString`，不跑 `onMounted`，所以
   所有"有数据"的分支（表格行、evidence、时间线、gates、进度数字）在冒烟里都是
   空态。已用静态核对补足：i18n 双语键 849/849 对齐、所有 `t('…')` 字面 key 全部
   解析（脚本逐文件核对）、模板里的图标名全部存在于 `@element-plus/icons-vue`、
   组件名全部来自 Element Plus / 本切片文件。**行级渲染仍未被真实执行过。**
2. **轮询。** `setInterval` 只在提交导入/同步后启动，jsdom 冒烟不触发。2s 间隔、
   终结态停止、失败后继续重试没有自动化用例。
3. **对话框内容。** `el-dialog` 默认插槽在 SSR 不渲染，决策对话框的
   `el-date-picker` / 单选组 / `confirmed_by` 校验分支没有渲染级验证。
4. **没有截图。** 视觉验收（blocking 行红色左边框与浅红底、debt 行警告色、只读
   徽标等）需要人工看一眼。
5. **未做端到端联调。** 未启动后端发真实请求；§2 的字段对照是**读代码**得出的，
   不是跑出来的。建议集成阶段至少在 smoke 之外跑一次导出后的 `make gates`。
6. **`wontfix` / `false_positive` 的第二人确认只是"填人"**：UI 要求填
   `confirmed_by` 并校验不等于当前用户，真正的身份确认（对方确实同意）在流程上
   仍需人工，服务端只能校验用户名不同。
