## ① `routes/__init__.py` 要插入的精确片段（留档）

约定：Agent Hub 蓝图与 `hub_bp` / `npm_bp` / `docs_bp` 一样**注册在裸 prefix**，
每个 view 自己声明完整路径（`/api/v1/repos…`）。不要注册到 `api + "/repos"`。

```python
# 顶部导入段（与其它 auth.permissions 常量一起）
from auth.permissions import (
    ADMIN_ROLES, ADMIN_VIEW, AGENT_RUN, APP_READ, FINDING_READ, REPO_READ,
)

# register_all() 内的本地导入
    from routes.repos import repo_bp
    from routes.repo_context import repo_context_bp
    from routes.findings import findings_bp
    from routes.agent_tasks import agent_tasks_bp
    from routes.repo_webhook import repo_webhook_bp

# ── Auth guards（必须在 register_blueprint 之前）──
    # 蓝图级 guard 是**地板**，更细的权限点由各 view 自己带
    # （import/sync 带 repo:write，git-credential 带 repo:push…）。
    repo_bp.before_request(require_permission(REPO_READ))
    repo_context_bp.before_request(require_permission(REPO_READ))
    findings_bp.before_request(require_permission(FINDING_READ))
    agent_tasks_bp.before_request(require_permission(AGENT_RUN))
    # repo_webhook_bp **刻意不加** guard：Forgejo 是无会话的机器调用，
    # 它的凭据是 §5.4 的共享密钥 HMAC。它同时列在
    # scripts/check_auth_guards.py 的 PUBLIC_ENDPOINTS 里，让这个决定可见。

# ── 注册（与其它裸 prefix 蓝图并列）──
    app.register_blueprint(repo_bp, url_prefix=prefix)
    app.register_blueprint(repo_context_bp, url_prefix=prefix)
    app.register_blueprint(findings_bp, url_prefix=prefix)
    app.register_blueprint(agent_tasks_bp, url_prefix=prefix)
    app.register_blueprint(repo_webhook_bp, url_prefix=prefix)
```

`routes/repo_webhook.py` 的 view 带 `@api_operation(..., security=[])`，这是
`check_auth_guards.py`「匿名是深思熟虑的」的判定依据；删掉它会让该门禁（正确地）报红。

§5.4 决策表：`push` 到默认分支且 policy 允许 → `review`（priority 5）；
`issues` 带 `agent` label → `fix`（priority 8）；`pull_request` merged → `backfill`
（priority 3，文档回写；S0 的 `TASK_KIND` 里没有 "docs"）。未识别事件返回 200
`handled: false`（不能让 Forgejo 无限重试）；仓库不存在 → 404 且日志留痕。

## ⑥ 与规格的偏差 / 集成方需要知道的点

1. **`git-credential` 端点**：§5.3 的清单里没有它，但 §5.2 要求 API 侧签发 git 凭据；
   集成方已在 `routes/repos.py` 追加。实现走 `ApiKeyManager`（与 pip/npm 同一套凭据，
   不新建第二套），只读镜像（`kind=="upstream"`）返回 409。
2. **`include_prs` 不入库**：S0 的表里没有该列，开关存在 `ImportJob.cursor` 的 JSON 中。
3. **`FORGEJO_GIT_BASE_URL` 是我加的**：commit 的 git 回退路径从**容器内**地址 clone，
   而不是走边缘 nginx 的 `/git/`（少一跳）。留空即用 `FORGEJO_BASE_URL`。
4. **commit 元数据默认走 Forgejo API**（`/api/v1/repos/<r>/commits`，分页）；
   API 失败才退回 `GitCommitReader` 的只读裸副本 + `git log`。两条路都只读，
   都没有 pygit2 / dulwich / GitPython。
5. **`fingerprint_source_paths()` 只回传文件路径**，不含行号/时间——§4.4 是 S3 的事，
   这个函数只是为了把边界写清楚。

## ⑦ 风险与不确定点（建议主智能体与运维确认）

1. **push 的凭据链没有闭合（最高优先）**。`/git/…/info/refs?service=git-receive-pack`
   的 `Authorization` 由 **Forgejo** 校验，而 `git-credential` 发的是 **openfish
   API key**。§5.2 说"复用现有 API-key 校验"，但 Forgejo 默认不认识 openfish 的 key：
   要么给 Forgejo 配一个外部认证委派（把 Basic 用户名/口令转给 openfish 校验），
   要么让 `git-credential` 改为铸造一串 **Forgejo** token（新依赖：Forgejo API
   `/users/{u}/tokens`）。当前实现满足"clone 公开镜像"与"凭据只落一次、只存哈希"，
   **push 端到端未验证**；这是 §10 的 open question，不是 S1 能单独拍板的。
2. **Forgejo tag 版本**：规格 §2.2 写 `:9`，但 v9 已于 2025-01-16 EOL；`docker/forgejo/`
   默认 `:15`（LTS，EOL 2027-07-15）。镜像名 `codeberg.org/forgejo/forgejo`。
   如果内网只能拿到 Docker Hub 的 `forgejo/forgejo`，改一个变量即可（README 已写）。
3. **`ROOT_URL=/git/` 与 nginx 无 rewrite**：我按"Forgejo 自己处理子路径"配置。
   若实测页面资源 404，说明需要给 ROOT_URL 加子路径 rewriting（`sub_filter` 或让
   Forgejo 监听 `/git/` 前缀），请以实测为准改 `docker/nginx/nginx.conf`。
4. **migration 完成判定**是尽力而为：Forgejo 没有稳定的 `migrating` 字段，我读
   `migrating` / `migration_status`，都不认识时以"仓库可读"作为完成。最坏情况是
   早一点进入 mirror_issues（此时 issue 分页可能偏少），下一次 `sync` 会补齐——
   upsert 幂等，不会产生重复行。
5. **issue 分页用 offset 语义**：`stream_issues(offset=…)` 一次只取"未消费的下一页"，
   游标同时保留 `issue_number`（防御源系统重编号）与 `issues_seen`（源行 offset）。
   若 Forgejo 在 migration 进行中返回**非稳定顺序**，某一页可能漏读一行；
   `sync` 重跑会补上（幂等 key = `source_id`），但**首次导入的计数可能少几条**。
   发现该现象时把 `IMPORT_POLL_ATTEMPTS` 调大，让 migration 完全结束后再镜像。
6. **webhook 的自动 review 默认开**（policy 读不到时 `True`）。这与 §7.2 的
   `defaults.auto_review: true` 一致，但意味着 S3 的 policy 服务一旦落地，
   `read_policy_auto_review` 的候选函数名必须对得上（见 ④ 最后一行）。
7. **`check_contract.py` 需要活服务器**，我没有跑；`check_openapi.py`（117 个
   operationId、30 个 $ref 全解析）在我的改动后是绿的。
