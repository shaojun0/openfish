# S6 集成说明（git push 凭据链闭合）

> 本切片闭合 `docs/agent-hub/DEVELOPMENT.md` §13.1 的最高优先开放问题：
> `git-receive-pack` 的 HTTP Basic 由 **Forgejo** 校验，而旧端点铸造的是
> openfish API key，所以 clone 能过、**push 必 401**。
>
> 方案（已拍板，本文件不再讨论替代方案）：openfish 仍是身份权威，用平台的
> Forgejo admin token 为每个平台用户**懒创建**一个 Forgejo 账号并铸一张
> Forgejo access token。该 token 加密落库，按用户隔离，可单人撤销。

## ② 部署方必须做的配置

### ②.1 Forgejo admin token 的 scope（最小权限）

平台 token 要能调 `/api/v1/admin/users` 和替用户调 `/api/v1/users/{u}/tokens`，
按 [Forgejo Access Token Scope](https://forgejo.org/docs/latest/user/authentication/token-scope/)
属于 `/admin/*`，**至少需要 `write:admin`**（`write:` 覆盖对应的 `read:`）。

```bash
# 推荐：最小权限
docker exec -u git openfish-forgejo \
  forgejo admin user generate-access-token \
  --username openfish-admin --token-name openfish-platform \
  --scopes write:admin --raw

# 也接受 all，但过宽；docker/forgejo/README.md 的旧命令用的是 all
```

> `write:admin` 能让平台建用户、铸票、删用户。**不要**把平台 token 交给最终用户。

最终用户拿到的那张票由平台铸造，只带仓库 scope：

| 场景 | scope |
|---|---|
| `kind=workspace`（可写工作仓） | `write:repository` |
| `kind=upstream`（只读镜像） | `read:repository` |

用户票**永远不含任何 admin scope**；门禁对此有断言
（`scripts/check_git_identity.py` 的 "no user ticket ever carries an admin scope"）。

### ②.2 `GIT_IDENTITY_KEY`（Fernet 主密钥）

token 加密存储用的主密钥。**缺失时 `GET /api/v1/repos/<slug>/git-credential`
返回 503**，不会降级成明文。

```bash
# 任意高熵字符串即可（服务端会做 urlsafe_b64encode(sha256(secret)) 派生出
# 32 字节 Fernet key，所以不必是 Fernet.generate_key() 的格式）
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

把输出写进 `docker/.env`（600 权限，**不进仓库**）。派生逻辑写在
`TokenCipher` 的 docstring 里：换密钥等于所有已存 token 无法解密（会被识别为
不可读并轮换），所以密钥要按“长期有效”对待，不要随手改。

### ②.3 compose 需要追加的环境变量

S1 的 `x-backend-env` 片段已经带了 `FORGEJO_BASE_URL` / `FORGEJO_ADMIN_TOKEN` /
`FORGEJO_OWNER` / `FORGEJO_PUBLIC_BASE_URL`。本切片只需要再加一行：

```yaml
  # ── Agent Hub：git 凭据兑换（S6）────────────────────────────────
  # 加密存储 Forgejo token 的 Fernet 主密钥；缺失时 git-credential 返回 503。
  GIT_IDENTITY_KEY: ${GIT_IDENTITY_KEY:-}
```

`docker/.env` 里对应 `GIT_IDENTITY_KEY=<②.2 生成的值>`；`FORGEJO_ADMIN_TOKEN`
沿用 `docker/forgejo/README.md` 第 4 节的两处写入（`forgejo.env` 与 `docker/.env`）。

### ②.4 等价 CLI 引导路径（没有 admin token 时）

Forgejo CLI 原生支持“建用户并同时发 token”：

```bash
docker exec -u git openfish-forgejo \
  forgejo admin user create \
    --username of-<id>-<hash> \
    --random-password --must-change-password=false \
    --email of-<id>-<hash>@openfish.invalid \
    --access-token --access-token-name openfish-git \
    --access-token-scopes "write:repository"
```

这条路径只适合**手工排障**：平台自己的 `ensure` 在第一次请求时仍会
adopt 已存在的账号、删掉同名旧票并铸新票（Forgejo 不允许同名 token 重复），
所以平台不依赖它。生产应让平台用 REST + admin token 自动完成。

## ③ 身份模型与用户名规则（一旦上线不可改）

```
openfish user (users.id, users.external_id)
        │  FK users.id ON DELETE CASCADE
        ▼
git_identities (user_id, forgejo_username, external_id, token_ciphertext, …)
        │
        ▼
Forgejo account "of-<user_id>-<sha256(external_id)[:10]>"
```

```python
derive_username(user_id, external_id) -> f"of-{user_id}-{sha256_text(external_id)[:10]}"
```

* 只含 `[a-z0-9-]`，长度 ≤ 39；
* 同一个 `(user_id, external_id)` 永远得到同一个名字；
* 不同用户不会碰撞（`user_id` 唯一，且它就在名字里，所以即便两个
  `external_id` 的哈希前缀相同也不会合并账号）；
* `display_name` / `email` 作为 Forgejo 账号的 `full_name` / `email` 资料写入
  （`email` 缺省时用 `<username>@openfish.invalid`，RFC 2606 保留域，不会误发信）。

> ⚠️ **一旦上线不可改。** commit 归属、审计与“按人撤销”都挂在 Forgejo 账号名上；
> 改名会让该账号名下的历史提交归属断裂。要改规则，只能新增映射而不是重命名。

HTTP 契约（`GET /api/v1/repos/<slug>/git-credential`，权限点仍是 `repo:push`）：

```json
{
  "slug": "<owner>/<name>",
  "clone_url": "http://<host>/git/<forgejo_repo>.git",
  "username": "of-<id>-<hash>",
  "password": "<Forgejo access token>",
  "expires_at": "2026-…Z",
  "read_only": true,
  "kind": "upstream"
}
```

`username`/`password` 直接可用作 HTTP Basic；`read_only` 标出这张票的 scope。
`kind=upstream` 不再返回 409，改为返回只读票。

## ④ 撤销路径接在哪里

**结论：此前仓库里根本不存在“禁用/删除用户”的路径。**
`is_active` 只有读取（`auth/guards.py`），没有任何地方写入 `False`；`cli.py`
只有角色命令；`frontend/src/views/AccessView.vue` 只**展示** `is_active`，
没有开关。所以“接到既有禁用路径”无钩可接，本切片补了最小的那个钩子：

| 位置 | 行为 |
|---|---|
| `services/authz.py::AuthzService.set_active(user_id, value=True)` | `is_active` 的唯一写入点（新增） |
| `backend/cli.py::cmd_disable_user`（`cli.py disable-user <identity>`） | 先 `set_active(False)`，再 `GitIdentityService(Session).revoke(user_id)` |
| `backend/cli.py::cmd_enable_user`（`cli.py enable-user <identity>`） | `set_active(True)`；下次请求会重新兑换 token |
| `GitIdentityService.revoke(user_id, *, delete_forgejo_user=False)` | 调 Forgejo 删掉 token（名字 `openfish-git`）并写 `revoked_at`；`--delete-forgejo-user` 还会删账号 |

`revoke` 不需要 `GIT_IDENTITY_KEY`（按确定性用户名删除），所以密钥缺失时也能切断
访问。**但远端删除失败时 revoke 会抛错、且不写 `revoked_at`**（Forgejo access token
没有服务端 TTL，本地标记"已撤销"而远端票还在用是更坏的结果）：CLI 会打印
`git identity not revoked` 并返回失败，运维需重试。Forgejo 返回 404（票本来就不在）
按成功处理。`--delete-forgejo-user` 的账号删除是尽力而为——票已删即视为已切断。

**若以后新增 HTTP/UI 的禁用入口**，最小改法是在那个 handler 里照 `cmd_disable_user`
调用两件事（`authz.set_active(user.id, False)` + `git_identity.revoke(user.id)`），
不要只置 `is_active`——否则被禁用的账号还能用旧票 push 到票过期为止。
`revoke` 的批量入口 `rotate_expired()` 也供 worker/CLI 调用，但**目前没有
定时器接它**（见 ⑦）。

## ⑤ 插件侧（DSH 企业内网插件）行为与限制

* `mirrorsFor()` 新增 `git` 条目，`applyMirrors()` 写两个文件：
  * `/usr/local/bin/openfish-git-credential`（插件生成，**700**，内含平台 key）；
  * `/etc/gitconfig`（`credential.helper` 指向它，并设 **`useHttpPath = true`**）。
* helper 是 Node 脚本，只用内置模块（无新 npm 依赖）。git 把动作作为 argv
  （`get`/`store`/`erase`），helper 在 `get` 时从 stdin 的 `path=` 解析
  `<owner>/<name>`，调 `<platformUrl>/api/v1/repos/<owner>/<name>/git-credential`
  （`Authorization: Bearer <平台 key>`）换取 Forgejo 票后按 git credential 协议输出。
* 同一 host 下不同仓库靠 `useHttpPath` + `path` 解析区分。
* 平台 URL 取自插件既有 `platformUrl`，owner/name 取自 git 传入的 path，**没有硬编码**。
* 失败（平台不可达 / 被拒）时**静默退出**：stdout 为空、exit 0，stderr 一行原因，
  不阻塞 git。
* `autoGitCredential`（默认 `true`，与 `autoMirrors` 同风格）：为 `false` 或停用
  企业内网模式时删除 helper（key 不留在盘上）；`/config` 接受 `auto_git_credential`。
* TLS 姿态与插件一致：`verifyTls=false` 时 git 侧写 `sslVerify=false`；
  配了 `caFile` 则写 `sslCAInfo`。

**限制**：helper 以文件形式持有平台 key，`700` 只挡普通用户，root / 同 uid 进程
仍可读；票是短期（默认 7 天）但 helper 本身不缓存，每次 git 需要凭据都会换一次。

## ⑦ 风险与不确定点

1. **Forgejo 铸票的 HTTP 形状（最高不确定）**。默认实现是
   `POST /api/v1/admin/users` 建账号 + `POST /api/v1/users/{u}/tokens`
   （带 `Authorization: token <admin>` 与 `Sudo: {u}`）。Forgejo 官方 API 文档把
   `/users/:name/tokens` 描述为需要 BasicAuth 的“特殊端点”，但 handler 用
   `ctx.User()`（路径里的目标用户）且 admin 可 Sudo。本仓库没有活的 Forgejo 可
   验证，门禁用假客户端跑。**上线前必须用真 Forgejo 验证一次 push**；若被拒，
   ②.4 的 CLI 路径可作运维兜底，或改用 BasicAuth（需要保存用户口令，不推荐）。
2. **并发**：进程内按 `user_id` 加锁 + `git_identities.user_id` 唯一约束 +
   `IntegrityError` 后重读，远端用 400/409/422 视为“已存在”再读。多进程/多副本
   由 DB 唯一约束兜底；SQLite 首次并发写可能遇到 `database is locked`（生产用
   PostgreSQL 不受影响）。门禁只覆盖单进程双线程。
3. **token 轮换**：Forgejo access token 没有服务端 TTL，`token_expires_at` 是本
   平台的记账；`token_for` 只在**被调用**时轮换，`rotate_expired()` 是批量入口但
   **没有定时器接它**——长期没有请求的用户，其 Forgejo 票会一直有效。若要真正的
   到期失效，应加一个 worker/CLI 定时任务调 `rotate_expired()`。
4. **轮换是先删后铸**：若删除成功而铸票失败，该用户在下一次请求前没有可用票
   （不会发生“旧票继续生效”）。下一次 `token_for` 会重建。
5. **用户名冲突**：派生规则含 `user_id`，正常不会撞；但若运维手工先在 Forgejo
   建了同名账号，`ensure_user` 会**adopt** 它（而不是报错）——理论上可被抢注。
   建议把 `FORGEJO_OWNER` 对应的组织/命名空间限制给平台。
6. **邮箱唯一性**：平台用户若带真实 `email`，而该邮箱已被一个 Forgejo 账号占用，
   建号会失败（502）。要绝对避免，改成始终用 `synthetic_email`。
7. **scope 是仓库无关的**：用户票是 `write:repository`，不绑定到具体仓库；平台的
   `repo:push` 校验只发生在**铸票那一刻**。分支保护仍由 Forgejo 独立承担（I4）。
8. **密钥轮换**：`GIT_IDENTITY_KEY` 一换，所有 `token_ciphertext` 都解不开，会被
   当作不可读并逐个轮换（旧票由 Forgejo 侧留着直到下次轮换删除）。没有迁移工具。
9. **审计**：commit 归属到 `of-…` 账号，人可读性靠 `full_name`；Forgejo 侧看不到
   “这是 openfish 的哪个用户”的直接映射（映射只在 `git_identities`）。
